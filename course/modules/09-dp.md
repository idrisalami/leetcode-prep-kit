This module covers dynamic programming. Module 07 ends on the point where backtracking turns into it ([07-backtracking.md](07-backtracking.md#when-it-stops-being-backtracking), §When it stops being backtracking), and on this rule:

> **You cannot memoise a search whose state includes "everything used so far": that state *is* the path, so no two nodes share it. Memoisation becomes possible exactly when the remaining problem has a small key.**

That rule is a definition of dynamic programming written as a prohibition. This module removes the prohibition. You'll learn to choose a state small enough for two routes to share, to write the recurrence as a sentence about the last decision, to pick base cases and sentinels that survive the combiner, to fill a table in an order its dependencies allow, and to state the cost as states times cost per state.

| | Backtracking (07) | Dynamic programming (09) |
|---|---|---|
| What you enumerate | the **paths** of a decision tree | the **distinct states** of the same tree |
| The mark | [the per-path mark](07-backtracking.md#the-per-path-mark): on while the item is on the path, off when it leaves | **permanent, and it holds an answer: the [BLACK mark of module 08](08-graphs.md#grey-is-the-per-path-mark-black-makes-it-permanent)** |
| What the mark says | *"am I standing on it right now?"* | *"this is already solved, and here is the answer"* |
| Two paths reaching the same node | **disagree**: they have different futures | **agree**: same future, so solve it once |
| The question | *"give me all the candidates"* | *"how many"*, *"what's the best"*, *"is it possible"* |
| Cost | exponential: leaves × cost per leaf | **polynomial: states × cost per state** |

> ⭐ **A DP recurrence is a backtracking decision tree with the memo put back.**

**And the memo is the BLACK mark.** Module 08's BLACK mark doubles as a memo on a DAG: it records "finished, and proven clean", and it is what keeps a dense DAG from going exponential. Module 07 takes its mark off on the way back up and pays for an exponential search. This module leaves the mark on, stores an answer in it, and gets polynomial time. Those are one fact read in two directions, and the state decides which one you're allowed.

The drill set at the bottom is not solved anywhere in this module. Every worked example uses a different problem.

**How to use it.** Read §0, then answer the self-check in §0.9 and re-read the parts of §0 behind any question you miss. Then work through the recurrence, the base cases and the iteration order, the four worked shapes, and do the drill set cold.

**DP is a graph traversal whose mark carries a value.** A memoised recursion is a DFS over an implicit DAG: the nodes are states, the edges are choices, and the memo is the BLACK mark with the answer written on it. The irreducible thing in module 06 was the traversal, in module 08 the visited set, in module 07 choose, explore, undo. **Here it is the state.** Every failure in §Common DP mistakes is a wrong answer to one question, and in this topic a badly chosen state is not a bug you can see: the code around it looks perfect and returns a confident wrong number.

**The one question this module answers:**

> *`dp[i]` is the answer to exactly which subproblem?*

Answer it in one sentence, with every index named and a unit, and the recurrence, the base cases and the return follow from it.

## 0.2 The structure and how it works

### Three marks, and what each one holds

| Module | Asks | The mark |
|---|---|---|
| 08, graphs | *"how do I stop **arriving** at the same node twice?"* | a permanent mark, `visited` |
| 07, backtracking | *"how do I enumerate every candidate exactly once?"* | a per-path mark |
| 09, DP | *"how do I stop **solving** the same subproblem twice?"* | a permanent mark that stores the answer: the memo |

The three differ only in what the mark holds: nothing (`visited`), nothing and only for a while (the per-path mark), and the answer (the memo).

> **A memo is a `visited` set whose elements carry a value.** Nothing else about the traversal changes.

### BFS or DP: ask what the mark carries

"BFS/DFS or DP?" is the wrong question. A memoised recursion is still a DFS, and the grid problems here are graph traversals. The container doesn't change; the mark does.

> **BFS: a node's value comes from whoever got there first. DP: a node's value comes from every predecessor, combined.**

BFS's whole theorem is *first arrival is final*. That is why one boolean mark is enough for it, and why it answers *reachable* and *fewest steps* and nothing else. So ask one question: *if I mark this node done on its first arrival, have I lost anything?* One grid, with moves right and down only, four questions:

| The question asked | Lost anything on first arrival? | Tool |
|---|---|---|
| *Can I reach the corner?* | no: one arrival is as good as any | BFS or DFS with `visited` |
| *Fewest steps to the corner?* | no: BFS's order makes the first arrival the shortest | BFS |
| *How many distinct paths to the corner?* | **yes**: every arrival contributes, and they must be summed | DP |
| *Cheapest path, with a cost on each cell?* | **yes**: the first arrival is no longer the cheapest | DP on a DAG (Dijkstra on a general graph: [08-graphs.md](08-graphs.md#dijkstra), §Dijkstra) |

⚠️ **Drop `visited` to fix rows 3 and 4 and you are enumerating paths, which is exponential. Keep it and you have thrown the multiplicity away.** The fix is neither: give the mark a value.

**The bound says the same thing.** A 100 × 100 grid has C(198, 99) ≈ 2.3 × 10⁵⁸ right-and-down paths from corner to corner (198 moves, of which you choose which 99 go down) and 10⁴ cells. A huge gap between the objects to count and the states to fill is what overlapping subproblems look like in the constraints. A statement that reassures you the answer fits in a 32-bit integer is telling you the answer is a large count, not a path.

**And where the two meet:** with moves right and down only, row-major order is a topological order of the cells, since both cells a cell reads come earlier in it. So the bottom-up table is a sweep of the DAG in topological order, carrying a number instead of a bit (§The iteration order). They are not rivals: DP is the traversal whose `visited` set got a value.

### The acid test

Module 08 ran this test to choose between a per-path mark and a permanent one ([08-graphs.md, §GREY is the per-path mark, BLACK makes it permanent](08-graphs.md#grey-is-the-per-path-mark-black-makes-it-permanent)). Here it runs the other way:

> **Can two different explorations disagree about the same node?**

| Answer | Example | So |
|---|---|---|
| **Yes**: the node's state depends on how you got there | *"used on this path"*, *"this letter is consumed"* | the state is the path: backtracking, exponential |
| **No**: the node has an answer of its own | *"the fewest squares that sum to 12 from here"* | cache it: DP |

Get *no* and you have just proved a memo is legal.

### The same tree, two questions

Take the subsets tree from [07-backtracking.md](07-backtracking.md#subsets), §Subsets, and change nothing but the question:

```python
def dfs(start):                      # the identical tree, both times
    for i in range(start, n):
        path.append(nums[i])
        dfs(i + 1)
        path.pop()
```

| The question | The full state of a node | Do two paths into `start = 3` agree? |
|---|---|---|
| *"return all subsets"* | **`(start, path)`**, and `path` differs on every route in | **no**: one arrived holding `[nums[0]]`, another holding `[nums[0], nums[1]]`, and their answers are different lists |
| *"how many subsets can be built from here?"* | **`start`** alone: `path` doesn't affect the count | **yes**: both futures are "every subset of `nums[start:]`", one number, cacheable |

**Same tree, same traversal, same code.** The only thing that changed is whether `path` is part of the state, and the question decides that, not the algorithm.

When the output is the candidates, the path is the answer, so the path is in the state, so no two nodes share a state, so a memo never hits. When the output is a count or a best, the path is history, and history is exactly what a memo is allowed to forget. That is why *"how many ways"* and *"the best"* are the signals against backtracking in [07-backtracking.md](07-backtracking.md#08-signals), §0.8 Signals: they are the two phrasings that remove `path` from the state.

### The overlap: draw it

Two conditions have to hold. The acid test gives the first: the future depends only on the state. The second is the one you can see:

> **The same subproblem is reached by more than one route.**

**Fibonacci, `n = 5`**, `f(n) = f(n - 1) + f(n - 2)`. Label every call with its argument, not its answer:

```
                          f(5)
                ┌───────────┴───────────┐
              f(4)                     f(3)          ← f(3) is here …
        ┌───────┴───────┐         ┌─────┴─────┐
      f(3)            f(2)      f(2)        f(1)     ← … and here. Same state.
   ┌────┴────┐      ┌──┴──┐   ┌──┴──┐
 f(2)      f(1)   f(1)  f(0) f(1) f(0)
┌──┴──┐
f(1) f(0)
```

**Count the labels.** There are 15 calls: `f(2)` and `f(0)` appear three times each, `f(1)` five times, `f(3)` twice. **The number of distinct labels is n + 1 = 6.**

The call count obeys `calls(n) = 1 + calls(n − 1) + calls(n − 2)`, with one call each for `n = 0` and `n = 1`, which works out to 2·F(n + 1) − 1, where F is the Fibonacci sequence itself. It grows by a factor of about 1.618 per step:

| n | Calls with no memo | Distinct states |
|---|---|---|
| 5 | 15 | 6 |
| 10 | 177 | 11 |
| 20 | 21,891 | 21 |
| 30 | 2,692,537 | 31 |
| 100 | about 1.15 × 10²¹ | 101 |

2ⁿ is an upper bound on that count, since each call makes at most two more and the depth is at most n, but it is not the count.

> **The memo doesn't make the tree smaller. It collapses the tree onto its set of distinct labels.** Each of the n + 1 states runs its body once; every other call is a lookup.

**And that is module 08's BLACK, on a different graph.** The DAG is this picture with the duplicates merged:

```
f(5) → f(4) → f(3) → f(2) → f(1) → f(0)
  └──────┴──────┴──────┴───────┘        every node reachable by many routes, computed once
```

> **A memoised recursion is a DFS over an implicit DAG whose nodes are states and whose edges are choices.** Module 07 said the same of the decision tree. This module is the case where the tree is really a DAG, and the memo is what notices.

### The test you can run in a room

> **Write the recursion. Then draw two levels of its tree and look for the same label twice.**

If a label repeats, the subproblems overlap and a memo pays. If no label ever repeats, a memo costs memory and buys nothing: that's divide and conquer, such as merge sort or binary search, not DP (§When it is not DP).

### What a state is

> **A state is the smallest description of "the rest of the problem" that determines the answer.**

Three words carry the weight:

| Word | Means | Fails when |
|---|---|---|
| **smallest** | drop anything the answer doesn't depend on | you keep `path`: 2ⁿ states, and you've written backtracking with a dict |
| **the rest** | what is left to decide, not what you have already done | you describe history and can't write a recurrence |
| **determines** | two histories with the same state have the same answer | you dropped something that mattered: a silently wrong answer |

Two tests, one sentence each:

> **The handover test:** if I hand you only the state, can you finish the problem?
>
> **The collision test:** if two different histories produce the same state, must they have the same answer?

Either test failing means your state is too small: you need another dimension. **The handover test passing with a state you can't enumerate means it isn't DP.** *"The set of cells already used"* passes it perfectly and has 2^(rows × cols) values (§The state is too big to enumerate).

> **When your state can't distinguish two situations you care about, add a dimension, not a special case.**

It is the rule from module 08's three colours ([08-graphs.md](08-graphs.md#stacked-special-cases-mean-the-structure-dropped-something), §Stacked special cases mean the structure dropped something), and here it is the most useful sentence in the topic. Stacked `if`s at the bottom of a DP are telling you the table is the wrong shape.

### The state sentence, before any code

Module 07 listed the state in three lines before writing a search. The DP form is the same three lines, with DP's nouns:

> **Line 1.** **`dp[i]` / `f(i, j)` is the answer to ⟨exactly which subproblem⟩**: every index named, with a unit.
>
> **Line 2.** **The recurrence is ⟨…⟩, because ⟨the last decision is …⟩.**
>
> **Line 3.** **The base case is ⟨…⟩, and the answer I return is ⟨which cell⟩.**

**Line 1 is a definition, not a description.** *"`dp[i]` is about the first i elements"* is not line 1: "about" defines nothing. *"`dp[a]` is the fewest perfect squares that sum to exactly `a`"* is.

⚠️ **The second half of line 3 is not decoration.** *Where does the answer live*, in `dp[n]`, in `max(dp)`, or in a cell you have to search for, is a separate decision from the recurrence, it is invisible in the code, and it goes wrong about as often (§The failure mode: a state that can't express the answer).

Line 1 must contain three things, every time:

| | Example |
|---|---|
| what each **index ranges over**, in the problem's nouns | *"`a` is an amount, 0 to n"*, not *"`a` is an index"* |
| whether the subproblem is **inclusive or exclusive** at the boundary | *"the first `i` characters"*, so `dp[0]` is the empty prefix, against *"ending at index `i`"* |
| the **unit** of the stored value | *"a number of squares"*, *"a count of ways"*, *"True if it can be done"* |

⚠️ **The inclusive or exclusive choice is where the off-by-ones come from, and you get to make it.** *"The first `i` characters"* is length-based: `dp` has `n + 1` entries and `dp[0]` is the empty case. It is almost always the easier one, because the empty subproblem becomes a real cell instead of a guard. A special case you design away beats one you handle.

## 0.3 Vocabulary

| Word | Meaning |
|---|---|
| **dynamic programming** | solving each distinct subproblem once and combining the stored answers, because the same subproblems recur |
| **state** | the smallest description of the rest of the problem that determines its answer: the arguments of `f`, or the indices of `dp` |
| **subproblem** | the problem a state stands for, such as "the fewest squares that sum to exactly 7" |
| **recurrence** | the rule that computes a state's answer from the answers of smaller states |
| **transition** | one edge of the recurrence: one choice, and the smaller state it leads to |
| **combiner** | how the terms of the recurrence are merged: `min`, `max`, `sum`, or `or` |
| **identity** | the combiner's value over nothing: `inf` for `min`, `-inf` for `max`, `0` for `sum`, `False` for `or` |
| **base case** | a state whose answer is written down, not computed, because the recurrence's assumption is false there |
| **sentinel** | the value stored for an impossible state; it must lose every comparison it enters |
| **memo, memoisation** | the cache from state to answer, and the technique of adding one to a recursion |
| **top-down** | a recursive function plus a memo; the call stack finds the order |
| **bottom-up, tabulation** | a loop that fills a table; you supply the order |
| **iteration order** | the order a bottom-up loop fills cells in; every cell read must already be written |
| **prefix state** | a state that covers a whole prefix, *"the first `i`"*; the answer is the last cell |
| **anchored state** | a state pinned to an end, *"ending at `i`"*; the answer is an aggregate over the table |
| **overlapping subproblems** | the same state is reached by more than one route |
| **optimal substructure** | the best answer is built from best answers to the parts, and swapping a part for a better one keeps it legal |
| **rolling array** | keeping only the rows or cells the recurrence still reads |
| **pseudo-polynomial** | polynomial in a numeric value, such as a target, rather than in the input's length |
| **interval DP** | a state that is a piece `s[i..j]`, filled by length |
| **mode** | an extra state axis drawn from a small fixed set, such as "holding" or "not holding"; a state machine |

## 0.4 Operations and their cost

**S** is the number of states. **k** is the number of choices one state combines.

| Operation | Python | Big-O | Trap |
|---|---|---|---|
| Memoise a function | `@cache` on a nested function | O(1) average per lookup, plus building the key | a `list` argument raises `TypeError: unhashable type: 'list'` |
| A hand-rolled memo lookup | `if key in memo: return memo[key]` | O(1) average, plus building the key | a tuple key is built and hashed on every access (§What to store the memo in: a matrix or a dict) |
| Read a cell of a table | `dp[i][j]` | O(1) | a negative index wraps round to the end of the row, with no error |
| Build a 1-D table | `[x] * (n + 1)` | O(n) | safe: the repeated element is immutable |
| Build a 2-D table | `[[x] * cols for _ in range(rows)]` | O(rows × cols) | `[[x] * cols] * rows` is one row with `rows` names (§Building the matrix: why the short form is broken) |
| Fill one state | the body of the recurrence | O(k) | not O(1) when the body loops over choices |
| A `min` over choices that may be empty | `min(gen, default=float('inf'))` | O(k) | without `default=`, `min` of nothing raises `ValueError: min() arg is an empty sequence` |
| Compare a slice inside a cell | `s[i:j] == s[i:j][::-1]` | O(j − i) | inside a double loop over `(i, j)` that is O(n³) |
| Roll two values | `a, b = b, a + b` | O(1) | as two statements, the second reads the new `a` |
| The whole DP | every state once | O(S × k) time | the cost per state multiplies; it is not 1 |
| The call stack, top-down | one frame per pending call | O(depth) space, on top of the memo | about 1,000 frames by default |

**The row people get wrong is "fill one state".** The count of states is usually right and the cost per state is left at 1. A loop, a comprehension, a slice or a `sum` inside the body multiplies the state count.

## 0.5 The primitives

Five moves build almost every DP solution. Each has an invariant: the thing that is true every time it runs.

**1. The memo.** The hand-rolled form, which `@cache` writes for you:

```python
memo = {}
def f(i):
    if i in memo:                        # is this node BLACK?
        return memo[i]
    if <base>:
        return <identity>
    memo[i] = <recurrence>               # paint it BLACK, and store the answer
    return memo[i]
```

*Invariant:* a state is a key of `memo` exactly when its final answer has been computed, so each state's body runs at most once. Those two marked lines are `if color[u] == BLACK` and `color[u] = BLACK` from module 08, with a value attached. Nothing else about the DFS changed.

**2. The padded table.** One extra row and column, for the empty prefixes:

```python
dp = [[<base>] * (n + 1) for _ in range(m + 1)]     # row 0 and column 0 are the empty prefixes
```

*Invariant:* `dp[i][j]` is the answer for the first `i` items of one input and the first `j` of the other, and row 0 and column 0 already hold the empty cases, so the body reads `dp[i - 1][...]` and `dp[...][j - 1]` with no boundary `if`. The price is the offset: `dp[i][j]` describes `a[i - 1]` and `b[j - 1]`.

**3. The sentinel.** An impossible state holds a value that loses every comparison:

```python
dp = [float('inf')] * (n + 1)            # for a min; float('-inf') for a max, 0 for a count, False for or
```

*Invariant:* a cell still holding the sentinel is exactly a state no sequence of choices reaches, and the combiner never picks it over a real value. The value the problem wants for "impossible", such as `-1`, is written only at the return.

**4. The iteration order.** Read it off the cells the body reads:

```python
for i in range(1, n + 1):                # the body reads dp[i - 1] and dp[i - 2]: smaller, so ascending
    dp[i] = <combine>(dp[i - 1], dp[i - 2])
```

*Invariant:* every cell the body reads was written on an earlier iteration. A cell that wasn't still holds its initial value, and the loop uses it with no error (§The iteration order).

Rolled into one row, a 0-1 knapsack must loop the capacity descending. Ascending reads cells the current item has already updated, so the item is used again, which is the unbounded version: with weights `[3]` and total 6, `dp[6]` becomes `True` where the 0-1 answer is `False`. No error, because every read is a legal index holding a legal, wrong, value.

**5. The rolling array.** Keep only what the recurrence still reads:

```python
a, b = dp0, dp1
for i in range(2, n + 1):
    a, b = b, <combine>(a, b)            # the whole right-hand side is evaluated before either name is bound
```

*Invariant:* at the top of the iteration for `i`, `a` holds `dp[i − 2]` and `b` holds `dp[i − 1]`; after it, `b` holds `dp[i]`. It only works when the recurrence reaches back a fixed, small distance (§The rolling array).

## 0.6 Inputs that break it

| Input | What breaks | Check |
|---|---|---|
| Empty input | the table has one cell, the loop doesn't run, and the answer is whatever `dp[0]` was set to | the empty problem is a real base case; is its value right for this combiner? In a counting DP it has exactly one solution, doing nothing, so it is worth 1, while a state with no legal move is a sum over nothing, the identity, 0. Seed the empty problem with 0 and every count comes out 0 |
| One element | a loop that starts at 2 never runs; the answer is a seed | trace n = 1 |
| The smallest input where the recurrence fires | the first cell computed from the seeds is where a wrong seed shows | trace `i = 1` or `i = 2` by hand |
| An impossible instance | `inf` returned where the problem wants `-1` or `0` | translate the sentinel at the return, and nowhere else |
| A state that can go negative | `dp[-1]` reads the last cell of the table | guard the index, offset the state, or use a dict |
| A recursion more than about 1,000 calls deep | `RecursionError` on the largest input only | the depth is a number you can compute ([08-graphs.md](08-graphs.md#recursion-depth-is-arithmetic), §Recursion depth is arithmetic); go bottom-up |
| A numeric bound such as a target of 10⁹ | a table of a billion cells | the DP is pseudo-polynomial; read the bound before choosing it |
| A move that can go back, such as 2 forward or 2 back | the memo is asked for a state still being computed: infinite recursion | name the measure that strictly decreases (§Something must shrink, and the states must form a DAG) |
| All values negative, such as `[-3, -1, -2]` | an answer seeded with `0` returns `0` instead of `-1` | seed with the first element or the sentinel, not with 0 |
| A greedy that passes every example | a wrong answer on the hidden tests | prove the exchange argument, or write the DP (§When it is not DP) |

## 0.7 Complexity, out loud

Say these as sentences, with the reason:

- **Time:** *"O(\_\_), because there are \_\_ states and each one costs \_\_ to fill."* It is the count-times-cost template you already use: V + E nodes and edges in module 08, leaves × cost per leaf in module 07, and here states × cost per state.
- **Say it in the problem's nouns.** *"n states"* is a number. *"One state per amount from 0 to the target"* is an analysis. The number of states is the product of the ranges of the parameters: `f(i)` with `i` in `0..n` has n + 1, `f(i, j)` over two strings has (m + 1)(n + 1).
- **The cost per state is the blank people skip.** An inner loop over k choices makes it O(k); looking back at every earlier index makes it O(n), so O(n²) in total.
- **Space:** *"O(\_\_), because the table is \_\_, and I can cut it to \_\_ with a rolling array."* The table is auxiliary space and it counts. Top-down also pays the recursion stack, O(depth), on top of the memo.
- **Pseudo-polynomial, by name.** `f(i, remaining)` has n × target states, which depends on the value of the target, not on the input's length. *"It's O(n · target), polynomial in the target's value but exponential in the number of digits used to write it, so it's fine because the constraint bounds the target at 10⁴."*
- **Optimality:** *"Any correct algorithm has to read every input element at least once, because an unread element could change the answer, so Ω(n) is a floor. My DP is O(n · k); the k is the price of the decision at each position."* Then name the upgrade you'd look for: an inner search that could be O(log k) with a sorted structure.

## The failure mode: a state that can't express the answer

**This is the one to fear.** It never crashes, the loop is perfect, and the number is wrong.

### Worked: Maximum Subarray (LC 53)

[Maximum Subarray](https://leetcode.com/problems/maximum-subarray/) (LC 53). *Find the contiguous, non-empty subarray with the largest sum.*

**The natural first state, and it is a dead end:**

> *"`dp[i]` is the largest sum of any subarray inside `nums[0..i]`."*

Run the handover test. You are handed `dp[i - 1] = 6`. Now compute `dp[i]`.

**You can't.** To know whether `nums[i]` extends the best subarray, you need to know **whether that best subarray ends at `i - 1`**, and the state threw that away. The definition is true, it is useful, and **no recurrence can be written for it.**

**The state that works:**

> *"`dp[i]` is the largest sum of a subarray that **ends at index `i`**."*

Now the handover works, because a subarray ending at `i` either extends the best one ending at `i - 1` or starts fresh at `i`. Extending pays only when that best sum is positive:

```python
def max_subarray(nums):
    dp = [0] * len(nums)
    dp[0] = nums[0]                              # the only subarray ending at 0 is [nums[0]]
    for i in range(1, len(nums)):
        dp[i] = nums[i] + max(dp[i - 1], 0)      # extend, or start over at i
    return max(dp)
```

> **"Ending at `i`" is the move that turns a description into a recurrence.** It makes the last decision expressible: *either extend, or start over.* A state that says "somewhere in the prefix" has no last decision.

**And the price is line 3:**

| | `dp[i]` = best in `nums[0..i]` | `dp[i]` = best **ending at** `i` |
|---|---|---|
| Recurrence | **none you can write** | one line |
| The answer is | `dp[n - 1]` | **`max(dp)`** |

⚠️ **Anchoring the state to "ends at `i`" moves the answer from the last cell to the maximum over all cells.** Write the good recurrence, then `return dp[-1]`, and on `[-2, 1, -3, 4, -1, 2, 1, -5, 4]` you get **`5` instead of `6`**. No crash.

**Traced:**

| i | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| `nums` | −2 | 1 | −3 | **4** | −1 | 2 | **1** | −5 | 4 |
| `dp` | −2 | 1 | −2 | **4** | 3 | 5 | **6** | 1 | 5 |

`max(dp) = 6`, at `i = 6`: the subarray `[4, -1, 2, 1]`, from index 3 to 6. `dp[-1] = 5`, the best subarray that ends at the last index, `[4, -1, 2, 1, -5, 4]`. **The table is right and the return is wrong.**

Two more inputs, both from §0.6: on `[-3, -1, -2]` it returns `-1`, because `dp[0]` is seeded with the first element and not with 0; on `[5]` the loop never runs and it returns `5`.

> **The rule: if the state is anchored ("ends at `i`", "uses item `i`", "is in mode `m`"), the answer is an aggregate over the table. If the state is a whole prefix ("the first `i`"), the answer is the last cell.** Say which one you have, in line 3, before you write the loop.

**Some problems have exactly this shape.** You recognise them because the recurrence you want to write needs a fact your state doesn't carry, and **the fix is to anchor the state, then aggregate at the end.**

## Overlap and optimal substructure

The vocabulary is *overlapping subproblems* and *optimal substructure*. **Neither is useful as a phrase.** Both are useful as a test.

### Overlapping subproblems: "is the same subproblem reached twice?"

**The test:** write the brute-force recursion, draw two levels, look for the same label twice (§The test you can run in a room).

**The shortcut test:** *count the distinct states, and compare that with the number of calls the plain recursion makes.* Fibonacci at `n = 30` has 31 states and makes 2,692,537 calls (§The overlap: draw it). **A gap that big is the memo's entire value.**

**No overlap, no memo.** Merge sort splits into two halves that share nothing, so a memo would never hit.

### Optimal substructure: "is the best answer built from best answers to the parts?"

**The test is an exchange argument:**

> **If I swap the piece I used for a *better* solution to that same subproblem, is my answer still legal, and at least as good?**

If yes, the problem has optimal substructure, and you may take the best sub-answer and forget the rest.

**The counterexample that makes it concrete:**

| | Optimal substructure? |
|---|---|
| **Shortest** path in a graph with non-negative weights | **yes**: any sub-path of a shortest path is a shortest path between its own ends, or swapping in a shorter one would shorten the whole. That is why Dijkstra works ([08-graphs.md](08-graphs.md#dijkstra), §Dijkstra) |
| **Longest *simple* path** | **no**: glue two optimal sub-paths together and they may share a node, so the result isn't even a simple path |

> **Longest simple path fails because the pieces are not independent: using a node in one piece forbids it in the other.** That coupling *is* "the state includes everything used so far". It is why longest simple path is NP-hard (a simple path with V − 1 edges exists exactly when the graph has a Hamiltonian path, so a fast algorithm for one would be a fast algorithm for the other) while shortest path is polynomial. It is the same line as the one between backtracking and DP.

**The practical version of the test:** *when I make one choice, is what's left a clean, self-contained instance of the same problem?* If a choice leaves a remainder that remembers what you did, it isn't DP yet: you need a bigger state or a different decomposition.

### The two-by-two that names the territory

| | **Overlapping subproblems** | **No overlap** |
|---|---|---|
| **Optimal substructure** | **dynamic programming** | **divide and conquer**: merge sort, binary search |
| **No optimal substructure** | **backtracking, or brute force**: the state is the path | brute force |

**Greedy is a fifth box, inside the DP one.** When one choice is provably right at every step, you don't need to try them all, so you don't need a table (§When it is not DP).

## Writing the recurrence

### The last decision

> **Enumerate the LAST decision, not the first.**

This is the technique that makes recurrences fall out. You are standing on a finished answer for state `S`. **Ask: what was the final choice that produced it?** Every possible final choice gives you one term, and the recurrence is the `min`, `max`, `sum` or `or` over those terms.

**The template sentence:**

> *"To solve ⟨state⟩, the last decision is ⟨what⟩. My options are ⟨list them⟩. If I choose ⟨c⟩ I pay ⟨cost⟩ and what remains is ⟨a smaller state⟩. So `dp[S] = ⟨combine⟩ over c of (cost(c) + dp[S after c])`."*

**Four instances, all written out further down, so the shape is visible:**

| Problem | The last decision | Terms |
|---|---|---|
| Perfect squares: the fewest squares summing to `a` | *"which square did I add last?"* | one per square ≤ `a` |
| Minimum path sum on a grid, moves right and down | *"did I enter this cell from above or from the left?"* | 2 |
| Maximum subarray, anchored at `i` | *"did the subarray ending at `i` extend the one ending at `i − 1`, or start here?"* | 2 |
| Longest common subarray ending at `(i, j)` | *"do the last two elements match? then extend the run ending one back in both"* | 1, or 0 on a mismatch |

### The three combiners

The question decides the combiner, and the combiner decides the empty problem's value.

| The question is | Combine with | The empty problem's value |
|---|---|---|
| *"how many ways"* | **`sum`** | **1**: there is exactly one way to do nothing |
| *"the best, the fewest, the most"* | **`min`** or **`max`** | **0**, or the identity for your cost: doing nothing costs nothing |
| *"is it possible"* | **`or`**, `any` | **`True`**: the empty thing is trivially achievable |

⚠️ **`dp[0] = 1` in a counting problem is not a hack.** It says *"there is one way to build nothing: choose nothing."* `dp[0] = 0` would say there is no way to build nothing, which is false, and every count built on it comes out 0. That reads as a loop bug, and it isn't one.

### The empty problem and the empty choice set

**They are one step apart in the code and they take opposite values.**

| | Means | Counting | `min` | Feasibility |
|---|---|---|---|---|
| **The empty problem**: nothing left to decide | *"I'm done"* | **1**, the empty solution | **0**, doing nothing costs nothing | **`True`** |
| **The empty choice set**: a state with no legal move | *"dead end"* | **0**, no way out of here | **`inf`** | **`False`** |

**The empty choice set takes the identity of the combiner.** A `sum` of nothing is 0, a `min` of nothing is `inf`, an `or` of nothing is `False`, and that is what `sum(...)`, `min(..., default=float('inf'))` and `any(...)` already return over an empty generator ([python-toolkit.md](../reference/python-toolkit.md#empty-safe-built-ins-the-anti-special-case-set), §Empty-safe built-ins: the anti-special-case set). Plain `min(...)` over an empty generator raises `ValueError: min() arg is an empty sequence`, so a `min` needs the `default=`. **The empty problem does not take the identity.** It is a real base case, and you have to write it.

> **`dp[0] = 1` and "zero ways from a dead end" are both right at the same time.** Confusing them is what makes a counting DP return 0 everywhere.

### Something must shrink, and the states must form a DAG

> **Something must shrink, an index, a budget, a remaining length, or there is no base case and no valid iteration order.** Name it out loud.

`dp[i]` reading `dp[i]` is a table that can never be filled. `f(i)` calling `f(i)` is a `RecursionError`. In backtracking this failure was `dfs(start)` called with `start` unchanged; here it is the same failure in a table.

**Here it also decides whether the cache is legal.** Take a recurrence whose moves are "2 forward or 2 back": `f(0)` calls `f(2)`, which calls `f(0)`.

> **A memo is only legal if the states form a DAG.**

**No set of base cases fixes a cycle.** `f(0)` is still being computed when `f(0)` is asked for again, so `if i in memo` never fires on it, and the recursion never bottoms out. **You can't seed your way out of a cycle.**

**But "the index must move one way" is the wrong generalisation.** The requirement is:

> **Some measure must strictly decrease along every edge, and it doesn't have to be a parameter of the state.**

A strictly decreasing measure makes a cycle impossible: going round one would bring the measure back to where it started, which a strictly decreasing quantity can't do.

| The measure | The moves look like | What it shows |
|---|---|---|
| An **index** | `f(i) → f(i + 1)`, `f(i + 2)` | linear 1-D DP |
| A **remaining budget** | `f(a) → f(a − s)` for each square `s ≤ a` | the state is a remaining amount, not a position, and it is what shrinks (§1-D DP) |
| An **interval length** | `dp[i][j] → dp[i + 1][j − 1]` | `i` goes up and `j` goes down, **neither is monotone**, and `j − i` is (§Interval DP) |
| **A value attached to each state** | any move at all, as long as it goes to a state with a strictly larger value | the moves can go in every direction and there is still no cycle |

**The last row refutes "only monotone moves".** You may move in any direction and still memoise, because the strictly increasing condition on every edge rules a cycle out.

⚠️ **So name the measure out loud.** If you can't name one, assume the state graph is cyclic and the memo is illegal. Then it's a shortest-path problem, solved with BFS, Dijkstra or a topological order, not a memoised DFS.

## Base cases and sentinels

> **A base case is a state where the recurrence's assumption is false.** There are two kinds, and they fail differently.

### Kind 1: the empty subproblem

The recurrence says *"remove one thing and recurse."* At the empty state there is nothing to remove. Its value comes from §The three combiners: `0` for a sum of costs, `1` for a count of ways, `True` for feasibility, `0` for a length.

> **Design the table so the empty case is a real cell.** Index by the *length of the prefix*, not by *position*, and `dp[0]` means the empty prefix, a legitimate entry the recurrence reads like any other. That is why two-sequence tables are `(m + 1) × (n + 1)`: **the extra row and column are the empty prefixes**, and they delete every boundary `if`.

```python
dp = [[0] * (n + 1) for _ in range(m + 1)]   # row 0 and column 0 ARE the base case
dp = [[0] * n for _ in range(m)]             # now every read of dp[i - 1][j - 1] needs a guard
```

⚠️ **`[[0] * n] * m` is `m` names for one row**, not `m` rows. This is the module where you build 2-D tables, so this is where it bites (§Building the matrix: why the short form is broken). **`[[0] * n for _ in range(m)]`, every time.**

### Kind 2: the impossible state, and the sentinel that survives your combiner

Some states have no answer: a total no subset of the items adds up to, a cell you can't reach. **The value you store there has to lose every comparison it enters.**

| Combiner | Sentinel | Why |
|---|---|---|
| `min` | **`float('inf')`** | `min(inf, x) == x` for every real `x`, so it never wins, and `inf + 1` is still `inf`, so it propagates |
| `max` | **`float('-inf')`** | the same, mirrored |
| `sum`, counting | **`0`** | zero ways contributes nothing to a sum |
| `or` | **`False`** | `False or x` is `x` |

⚠️ **`-1` is not a sentinel for `min`.** `min(-1, 5)` is `-1`, so "impossible" wins every comparison and poisons the table. **If the problem wants some special value returned for "impossible", translate at the very end**, `return <the impossible value> if dp[n] == INF else dp[n]`, and never let it inside the recurrence.

⚠️ **The mirror trap: a finite stand-in for infinity.** Python ints don't overflow, so `10**9` never wraps. But a finite stand-in only works while every real value stays below it: a sum of many large costs can pass `10**9`, and from then on "impossible" beats a real answer. **`float('inf')` is absorbing:** `1 + inf` is `inf` and `min(inf, x)` is `x`. The one operation to keep it out of is subtraction between two sentinels: `inf - inf` is `nan`, and every comparison with `nan` is `False`.

### A base case the recurrence can reach

If `dp[0]` is both a base case and something the loop writes, whichever runs second wins. **Initialise the base cases, then start the loop at the first index that isn't one.** A loop that begins at 0 and reads `dp[i - 1]` does not crash in Python: **`dp[-1]` reads the last cell of the table**, which holds its initial value or, worse, something left from an earlier row ([bug-checklist.md](../reference/bug-checklist.md#a-negative-index-wraps-instead-of-crashing), §A negative index wraps instead of crashing). An index that can go negative is not protected by "it would crash".

### The base cases to trace, every time

> **The empty input · a single element · the smallest input where the recurrence fires, usually `i = 1` or `i = 2` · the state the problem says is impossible.**

**Fifteen seconds, and it's where this topic's bugs are.** The loop body is usually right; the first two cells usually aren't.

## Top-down and bottom-up

**They compute the same thing.** Write whichever you can get right, know how to convert, and be able to say why you chose.

| | **Top-down: memoised recursion** | **Bottom-up: a table** |
|---|---|---|
| You write | the recurrence, literally, plus a cache | a loop that fills cells in a safe order |
| The iteration order | **the call stack finds it for you** | **you supply it, and it's a real decision** |
| Which states get computed | **only the reachable ones** | **all of them** |
| Base cases | an `if` at the top of the function | the initialisation of the table |
| Fails by | `RecursionError` at about 1,000 frames deep | reading a cell that isn't filled yet, **silently** |
| Rolling the array to save space | awkward | **easy** (§The rolling array) |
| Reconstructing the choices | awkward | easy: walk the table backwards |

### It is not about which end you start from

A memoised solution that counts from `n` down to 0 is top-down. Rewrite it to count from 0 up to `n`, still recursive, still cached, and it is **still top-down**.

> **Top-down vs bottom-up is whether you RECURSE or ITERATE. It has nothing to do with the direction the numbers run.**

**The test, and it takes one second:**

| | Look for |
|---|---|
| **Top-down** | a function that **calls itself**, plus a cache. **The call stack finds the order** |
| **Bottom-up** | a **`for` loop filling a table**. **You supply the order** |

Here is the grid from §The grid with its state flipped to *"the cheapest path from `(r, c)` to the bottom-right corner"*. It counts uphill, from the corner back to `(0, 0)`, and it is top-down:

```python
from functools import cache

def min_path_sum_uphill(grid):
    rows, cols = len(grid), len(grid[0])

    @cache
    def f(r, c):                         # the cheapest path from (r, c) to the corner
        if r == rows - 1 and c == cols - 1:
            return grid[r][c]
        best = float('inf')
        if r + 1 < rows:
            best = min(best, f(r + 1, c))
        if c + 1 < cols:
            best = min(best, f(r, c + 1))
        return grid[r][c] + best         # `def f` calling f(...): that is recursion

    return f(0, 0)
```

On `[[1, 3, 1], [1, 5, 1], [4, 2, 1]]` it returns 7, the same as the bottom-up version in §The grid. **Reversing the direction changes what the state means. It doesn't change the technique.**

### What reversing the direction is

| | `f(i)` is | What `i` holds |
|---|---|---|
| Downhill | *"the answer for the first `i` things"* | how much is **done** |
| Uphill | *"the answer from position `i` onward"* | how much is **left** |

**Both pass the handover test, and both are legitimate states.** Re-anchoring from *"what I've done"* to *"what's left"* is a real move, and a budget DP needs it: there the natural state is a remaining amount, not an index. It is worth practising on purpose. **It just isn't the top-down or bottom-up axis.**

⚠️ **The base cases mirror when you flip the state, for the same reason both times.** Fibonacci downhill seeds `f(0)` and `f(1)`, because `f(1)` would read `f(−1)` and a negative index isn't a state. Written uphill over positions `0..n`, a recurrence reading `f(i + 1)` and `f(i + 2)` seeds `f(n)` and `f(n − 1)`, because `f(n − 1)` would read `f(n + 1)`, past the end.

> **A recurrence that reaches `k` steps back needs `k` seeded cells**, and which end they sit at is decided by which way the state counts.

### Why the distinction is worth getting right

**The two real reasons to convert both live on the recurse-or-iterate axis.** Neither is visible on the direction axis:

| Only bottom-up can | Only top-down can |
|---|---|
| **drop the recursion stack**, the O(depth) of extra space that top-down pays on top of the memo | **skip unreachable states** |
| **roll the array** down to a row or a few values (§The rolling array) | **run when no simple loop order exists**, because the call stack finds the order |

> **"I reversed the direction" buys nothing. "I replaced the recursion with a loop" buys the stack and the rolling array.** If you can't tell which one you did, you can't say what the rewrite was for.

**When each is the better choice:**

| Prefer **top-down** when | Prefer **bottom-up** when |
|---|---|
| the state space is **irregular or graph-shaped** and no simple loop order exists | the order is obvious: left to right, small to large |
| **most states are unreachable**, and you want only the sparse subset | you want O(1) or O(n) space from a rolling array |
| you already wrote the backtracking version and are adding one decorator's worth of cache | the recursion would be deeper than about 1,000 frames |

> **The interview move:** state the recursion, say *"this is exponential because these subtrees repeat"*, add the memo, then say *"and the same recurrence can be written bottom-up if you want the space down."* That is brute force, then its complexity, then the optimisation, out loud, on a topic where the optimisation is mechanical.

### Top-down, in Python

```python
from functools import cache

@cache                                   # the entire memo
def f(i):
    if <base>:
        return <base value>
    return <combine>(<cost> + f(<smaller>) for <choice> in <choices>)
```

**`@cache` (Python 3.9 and later; `@lru_cache(maxsize=None)` before that) is a dict keyed by the arguments.** Two consequences to say out loud:

- ⚠️ **The arguments must be hashable**: `int`, `str`, `tuple`, `frozenset`. **A `list` argument raises `TypeError: unhashable type: 'list'`.** It is the same fact as putting a list in a set: set and dict members must be immutable ([python-toolkit.md](../reference/python-toolkit.md#dict-keys-must-be-immutable-convert-dont-invent), §Dict keys must be immutable: convert, don't invent). If a list is in your state, either it shouldn't be (§What a state is, *smallest*) or it becomes a `tuple`.
- ⚠️ **`@cache` on a method puts `self` in every key.** The cache is shared by the class, so it keeps every instance it has seen alive, and if the method reads its input from `self` and the same object is called again on new input, the old answer comes back. Use a nested function, the same shape you use for an accumulator ([bug-checklist.md](../reference/bug-checklist.md#mixing-a-method-and-a-nested-function), §Mixing a method and a nested function).

**The hand-rolled version is §0.5, primitive 1.** Be able to write it, because interviewers sometimes ask for it. What to store the memo *in*, a matrix or a dict, is a separate decision (§What to store the memo in: a matrix or a dict), and so is the mechanical conversion from one form to the other (§Converting top-down to bottom-up).

## The iteration order

**Bottom-up's only new decision, and it is mechanical.**

> **Write down which cells the recurrence READS. Every one of them must already be written. That is the whole rule.**

You don't reason about the algorithm. You look at the subscripts.

| The recurrence reads | So iterate |
|---|---|
| `dp[i - 1]` | `i` **ascending** |
| `dp[i + 1]` | `i` **descending** |
| `dp[i - 1]` **and** `dp[i - 2]` | `i` ascending, starting after the two seeded cells |
| `dp[r - 1][c]`, `dp[r][c - 1]` | rows ascending, columns ascending: the natural double loop |
| `dp[r + 1][c]`, `dp[r][c + 1]` | **both descending**: bottom-right to top-left |
| `dp[i][j - 1]` **and** `dp[i + 1][j]` | `i` descending, `j` ascending: the two axes go opposite ways, and it's still only the subscripts |
| **`dp[i + 1][j - 1]`**, an interval shrinking from both ends | **neither `i` nor `j` alone orders this.** Iterate by **length**: every interval of length 1, then 2, then 3 (§Interval DP) |

> **When no single index orders the dependencies, find the quantity they are monotone along.** For intervals it's `j − i`. It is the measure from §Something must shrink, and the states must form a DAG, used as a loop.

### The direction bug that has a name: 0-1 knapsack in one row

**This is the best-known iteration-order trap**, because it is a silent wrong answer that looks like a tidy optimisation.

Take a 2-D table `dp[item][capacity]` where each item may be used **at most once**, and compress it to one row:

```python
for item in items:
    for w in range(capacity, item.weight - 1, -1):   # DESCENDING
        dp[w] = max(dp[w], dp[w - item.weight] + item.value)
```

**Ascending is a different algorithm.** Going up, `dp[w - weight]` has already been updated by the current item, so the item can be taken again: **you have written unbounded knapsack.**

> **Descending reads the previous row. Ascending reads the current row.** One loop direction, two problems:
>
> | Direction | `dp[w - weight]` means | You have written |
> |---|---|---|
> | **descending** | the answer **without** this item | **0-1**: each item at most once |
> | **ascending** | the answer **possibly with** this item already | **unbounded**: reuse allowed |

**Seen on the smallest case.** One item of weight 3, and the question "which totals from 0 to 6 can be made?", with `dp[0] = True`. Descending leaves `[T, F, F, T, F, F, F]`: the item, used once, makes 3. Ascending leaves `[T, F, F, T, F, F, T]`: by the time `w = 6` reads `dp[3]`, the same pass has already set it, so the item is used twice.

⚠️ **And it doesn't crash or look wrong.** Module 07 put the same idea as "the index is two switches: change the one you meant to change" ([07-backtracking.md](07-backtracking.md#start-one-parameter-three-jobs), §`start`: one parameter, three jobs, and [07-backtracking.md](07-backtracking.md#the-index-is-two-switches), §The index is two switches). **Here the switch is a loop direction.**

### The failure when you get the order wrong

**Bottom-up reading an unwritten cell does not raise.** The cell holds its initial value, `0`, `inf`, or something stale from the previous row, and the answer comes out wrong with no signal. It is the same silent class as wrong bounds: the invariant is false, and every correct line after it is wasted ([bug-checklist.md](../reference/bug-checklist.md#bounds-or-state-that-cant-express-the-answer), §Bounds or state that can't express the answer).

> **The check, before running the loop: take the recurrence's rightmost read and ask "has that cell been written on an earlier iteration of these loops?"** Ten seconds.

## 1-D DP

### Worked: Perfect Squares (LC 279)

[Perfect Squares](https://leetcode.com/problems/perfect-squares/) (LC 279). *Given `n`, return the fewest perfect squares (1, 4, 9, 16, …) that sum to `n`.*

**First, the backtracking version, because that's where the recurrence comes from.** It is the target-sum-with-reuse template from module 07 ([07-backtracking.md](07-backtracking.md#every-template-in-one-place), §Every template, in one place, the row for a target sum with reuse allowed), with a `min` instead of collecting paths:

```python
def dfs(remaining):                       # the fewest squares summing to `remaining`
    if remaining == 0:
        return 0
    best = float('inf')
    for s in squares:                     # squares ascending
        if s > remaining:
            break
        best = min(best, 1 + dfs(remaining - s))
    return best
```

**Correct, and exponential.** Now run the acid test. Two different sets of squares can both leave `remaining = 7`. **Do they disagree about what happens next?** No: *"the fewest squares summing to 7"* is one number, and nothing about how you got to 7 changes it.

> **The answer depends on `remaining` and on nothing else. `remaining` is the state, and `path` is history.** The memo is legal.

**The three lines, before any code:**

> **Line 1.** **`dp[a]` is the fewest perfect squares that sum to exactly `a`**, for every amount `a` from 0 to n. One state per amount; the unit is a count of squares.
>
> **Line 2.** **`dp[a] = 1 + min(dp[a − s])` over every square `s ≤ a`**, because the last decision is *"which square did I add last?"*, and once `s` is used, what's left is the identical problem on `a − s`.
>
> **Line 3.** **The base case is `dp[0] = 0`**: zero squares sum to zero. **The answer is `dp[n]`**: the state is a whole subproblem, not an anchored one, so it's the last cell.

Line 2 named the loop, the `1 +` and the `min` before a character of code existed. That is the point of writing it first.

**Top-down:**

```python
from functools import cache

def num_squares(n):
    squares = [s * s for s in range(1, int(n ** 0.5) + 1)]

    @cache
    def f(a):                             # the fewest squares summing to exactly `a`
        if a == 0:
            return 0
        return min(1 + f(a - s) for s in squares if s <= a)

    return f(n)
```

**Three things to check by eye:**

| Check | Here |
|---|---|
| `f` takes **only** the state | a second parameter creeping in means the state isn't the smallest (§What a state is) |
| the base case **returns the empty problem's value** | a `min` over costs, so `0` |
| every recursive call has a **strictly smaller** argument | `s ≥ 1`, so `a − s < a`. **Say what shrinks** |

⚠️ **`min()` over an empty generator raises `ValueError`.** Here it can't happen, because `s = 1` qualifies for every `a ≥ 1`. **That is a precondition to notice and say**, not one to be lucky about. If every choice could exceed `a`, the call needs `default=float('inf')`.

**Bottom-up, in four mechanical steps** (§Converting top-down to bottom-up):

| Step | Here |
|---|---|
| 1. The parameters become the axes | `f(a)`, `a` in `0..n`, so **`dp = [float('inf')] * (n + 1)`** |
| 2. The base cases become the initialisation | `f(0) = 0`, so **`dp[0] = 0`** |
| 3. The body becomes the loop body | `min(1 + f(a − s))` becomes `min(1 + dp[a − s])` |
| 4. **The order** | the body reads `dp[a − s]` with `s ≥ 1`, **strictly smaller** indices, so **`a` ascending** |

```python
def num_squares(n):
    squares = [s * s for s in range(1, int(n ** 0.5) + 1)]
    dp = [float('inf')] * (n + 1)
    dp[0] = 0
    for a in range(1, n + 1):
        for s in squares:
            if s > a:
                break                     # squares is ascending, so nothing later fits
            dp[a] = min(dp[a], dp[a - s] + 1)
    return dp[n]
```

Both versions return 3 for `n = 12` (4 + 4 + 4), 2 for `n = 13` (4 + 9) and 1 for `n = 1`. Taking the largest square that fits at each step gives 9 + 1 + 1 + 1 for 12, four squares, which is why this needs a DP and not a greedy.

**Four things to notice, each one a bug from another topic:**

- **`dp[0] = 0` is written before the loop, and the loop starts at 1.** The base case is initialisation, not a branch in the body, and every cell the body reads at `a` is smaller than `a`, so it is already written.
- **`inf`, not `-1`.** `min(-1, x)` is `-1` and poisons everything downstream (§Kind 2: the impossible state, and the sentinel that survives your combiner).
- **`break`, not `continue`, because `squares` is sorted** ([07-backtracking.md](07-backtracking.md#sorting-turns-continue-into-break), §Sorting turns `continue` into `break`). That part is a constant factor, not a complexity class, and you should say which.
- **The `if s > a` test is a bounds guard as well as a prune.** Without it, `dp[a - s]` is a negative index, which Python reads from the end of the list instead of raising ([bug-checklist.md](../reference/bug-checklist.md#a-negative-index-wraps-instead-of-crashing), §A negative index wraps instead of crashing). **It is load-bearing for correctness**, and ranking a prune as class-changing, constant-factor or load-bearing is the habit from [07-backtracking.md](07-backtracking.md#rank-a-prune-before-writing-it), §Rank a prune before writing it.

**Complexity, out loud:**

> *"O(n√n) time: there is one state per amount from 0 to n, so n + 1 states, and filling one costs the number of squares that fit, at most √n. O(n) space: one entry per amount, and no rolling, because a cell reads `dp[a − s]` for many different `s`, so the whole prefix has to stay alive."*

That sentence fills all four blanks: the count, what the count is in nouns, the cost, and what the cost is.

⚠️ **The rolling-array question has a real answer here, and it is "no".** Knowing when the optimisation doesn't apply is worth as much as applying it, and the reason is one clause: **the recurrence reaches back an unbounded distance** (§The rolling array).

### The shape one delta away: a choice per index

The other 1-D family makes a choice at each index, and that choice constrains what was legal before it:

```python
dp[i] = <combine>(dp[i - 1],                          # option A: skip element i
                  dp[i - <reach back>] + value(i))    # option B: take it, which rules out some items before it
```

> **Two options, each O(1) to evaluate, so the DP is O(n) time, and because it reads a fixed number of earlier cells, it rolls to O(1) space** (§The rolling array).

**What makes this family distinctive:** *the choice at `i` constrains what was legal before `i`*. That constraint decides how far back the recurrence reaches, and reading the distance straight off the constraint is the skill. **Write line 2 as a sentence about the last decision, and the reach-back distance will be in the sentence before it is in the code.**

## The grid

### Worked: Minimum Path Sum (LC 64)

[Minimum Path Sum](https://leetcode.com/problems/minimum-path-sum/) (LC 64). *Move only right or down, from the top-left to the bottom-right of a grid of non-negative numbers, and minimise the sum of the cells on the path.*

**Why a grid is the friendliest DP there is.** The problem hands you the state: a cell. There is no design decision, and the legal moves fix the dependency direction, so the iteration order comes free too.

**The check that matters is optimal substructure's:** *are the pieces independent?* Here they are: once you stand on `(r, c)`, how you got there can't affect the cheapest continuation. The moves are right and down only, so the move graph is a **DAG**, and a DAG is a decision tree whose repeated subtrees are allowed to be shared.

⚠️ **If the moves went in all four directions, this would not be a DP over cells.** You could revisit cells, the state would have to include the visited set, and you'd be back in module 07. **"Right and down only" is not flavour text; it is the licence for the memo.** The constraints are part of the problem.

**The three lines:**

> **Line 1.** **`dp[r][c]` is the minimum path sum from `(0, 0)` to `(r, c)`, both included**, for every cell.
>
> **Line 2.** **`dp[r][c] = grid[r][c] + min(dp[r − 1][c], dp[r][c − 1])`**: the last decision is *"did I arrive from above or from the left?"*, and those are the only two ways in.
>
> **Line 3.** **The base case is `dp[0][0] = grid[0][0]`**, plus the first row and the first column, which each have one way in. **The answer is `dp[rows − 1][cols − 1]`.**

**The version with the boundary designed away.** Writing the first row and column by hand works, and costs extra loops. The better version pads the table so one recurrence covers every cell:

```python
def min_path_sum(grid):
    rows, cols = len(grid), len(grid[0])
    INF = float('inf')
    dp = [[INF] * (cols + 1) for _ in range(rows + 1)]   # one extra row and column
    dp[0][1] = 0                                         # the virtual entrance

    for r in range(1, rows + 1):
        for c in range(1, cols + 1):
            dp[r][c] = grid[r - 1][c - 1] + min(dp[r - 1][c], dp[r][c - 1])

    return dp[rows][cols]
```

On `[[1, 3, 1], [1, 5, 1], [4, 2, 1]]` it returns 7: the path 1 → 3 → 1 → 1 → 1.

**Read the padding:**

| Piece | What it does |
|---|---|
| row 0 and column 0 are **virtual cells outside the grid**, all `inf` | "arriving from outside" always loses the `min` |
| **`dp[0][1] = 0`** is the single door | it makes `dp[1][1]` compute `grid[0][0] + min(inf, 0)`, which is `grid[0][0]` |
| `dp[r][c]` corresponds to `grid[r − 1][c − 1]` | **the offset is the price of the padding, and it is the thing to get right** |

> **A constraint you make structurally impossible is a constraint you don't have to test.** The dummy head in a linked list, a `float('-inf')` sentinel, `hi = len(nums)` in a binary search, one recursion level per item in a backtracking search: each one designs a case away instead of handling it. Writing the first row and column by hand is the *handled* version; this is the *designed-away* version.

⚠️ **And the offset is exactly where this goes wrong.** Say which indexing you chose in line 1, *"`dp[r][c]` is the answer for `grid[r − 1][c − 1]`"*, or every read in the body is a coin flip. It is index-vs-value with two coordinate systems one line apart ([bug-checklist.md](../reference/bug-checklist.md#index-vs-value), §Index vs value).

**The iteration order, read off the subscripts.** The body reads `dp[r − 1][c]` and `dp[r][c − 1]`, both smaller, so rows ascending and columns ascending. That's the whole derivation.

⚠️ **Reverse the column loop and it still runs, still returns a number, and the number is wrong.** Run descending, `dp[r][c − 1]` hasn't been written yet on this row: it still holds its initial `inf`, so each cell sees only the path from above. On the grid above, every row comes out `inf` except its first column, the only cell the path straight down from the entrance reaches, and in the end `dp[3][3]` is `inf`. **No error.**

**Rolling it to one row.** The body reads only row `r − 1` and row `r`, so keep two rows:

```python
prev = [INF] * (cols + 1)
prev[1] = 0
for r in range(1, rows + 1):
    curr = [INF] * (cols + 1)
    for c in range(1, cols + 1):
        curr[c] = grid[r - 1][c - 1] + min(prev[c], curr[c - 1])
    prev = curr
return prev[cols]
```

**O(cols) space instead of O(rows × cols).** §The rolling array has the general rule and the one-row trap.

**Complexity, out loud:**

> *"O(rows × cols) time: one state per cell, and filling one is a `min` of two things, O(1). O(rows × cols) space for the table, or O(cols) with a rolling row, since the recurrence only reads the row above and the cell to the left. And O(rows × cols) is a lower bound: any cell left unread could hold the value that changes the answer, so I have to read every cell, and I match that."*

**On a grid, say "rows × cols", not "V + E"** ([08-graphs.md](08-graphs.md#grids-are-graphs), §Grids are graphs).

## Two sequences

### Worked: Maximum Length of Repeated Subarray (LC 718)

[Maximum Length of Repeated Subarray](https://leetcode.com/problems/maximum-length-of-repeated-subarray/) (LC 718). *Given two arrays, return the length of the longest subarray, contiguous, that appears in both.*

**The shape, and why the state is a pair of prefixes.**

> **When a problem involves two sequences and asks about aligning them, the state is *(how much of A I've consumed, how much of B I've consumed)*.** The table is `(m + 1) × (n + 1)`, and row 0 and column 0 are the empty prefixes (§Kind 1: the empty subproblem).

**Run the handover test.** You are told: *"you have used the first 4 elements of A and the first 6 of B."* Can you finish? **Yes**: everything still to decide involves only `A[4:]` and `B[6:]`, and the order you consumed the first ten things in doesn't matter. **Two prefix lengths are a state.**

**And the last-decision question is:** *"does `A[i − 1]` pair with `B[j − 1]`, or is one of them skipped?"* Two-sequence recurrences in general have up to three terms from that question. This problem's has fewer, because a contiguous run can't skip anything.

**The three lines, and the anchoring again:**

> **Line 1.** **`dp[i][j]` is the length of the longest common suffix of `A[:i]` and `B[:j]`**: the longest run that **ends exactly at** `A[i − 1]` and `B[j − 1]`.
>
> **Line 2.** **`dp[i][j] = dp[i − 1][j − 1] + 1` if `A[i − 1] == B[j − 1]`, else `0`**, because a contiguous common run that ends here must extend a common run ending one step back in both, and if the elements differ, no run can end here at all.
>
> **Line 3.** **The base case is row 0 and column 0, all zeros**: nothing ends at an empty prefix. **The answer is the `max` over the whole table**, not `dp[m][n]`.

⚠️ **Line 1 says "ends at", so line 3 says "max over the table".** It is §The failure mode in 2-D. `return dp[m][n]` returns *"the longest common run ending at the last element of both"*, which for `[1, 2, 3]` and `[3, 2, 1]` is **`0`** when the answer is **`1`**.

```python
def find_length(nums1, nums2):
    m, n = len(nums1), len(nums2)
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    best = 0
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if nums1[i - 1] == nums2[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1
                best = max(best, dp[i][j])         # the aggregate, taken as you go
    return best
```

On `[1, 2, 3, 2, 1]` and `[3, 2, 1, 4, 7]` it returns 3, the run `[3, 2, 1]`.

⚠️ **`[[0] * (n + 1) for _ in range(m + 1)]`, never `[[0] * (n + 1)] * (m + 1)`.** The second is `m + 1` names for one row, so writing `dp[1][1]` writes it in every row. On `[1]` and `[1, 1]` the aliased table returns 2, a run longer than the shorter array, where the answer is 1.

### Substring or subsequence: one branch and one return

The word in the statement decides two lines of the code:

| | Contiguous: substring, subarray | Subsequence: order kept, gaps allowed |
|---|---|---|
| `dp[i][j]` means | *"… the run **ending exactly here**"* | *"… the best over the whole pair of prefixes"* |
| On a **mismatch** | **reset to 0**: the run is broken | **not a reset**: skipping is allowed, so the cell still has a value. Which smaller prefixes it reads is the problem's to derive (row 9's candidate terms) |
| The answer is | **the `max` over the table** | **`dp[m][n]`**, the corner |

> **"Contiguous" is not a flavour of the problem. It is one line of the recurrence and one line of the return.** Read *contiguous*, *substring* or *subarray* in the statement and both lines are decided. Read *subsequence* and both flip.

**It is the lesson of §The failure mode, in 2-D**, and it states the general rule:

> **A contiguous problem forces an anchored state, and an anchored state forces an aggregate answer. A non-contiguous problem allows a prefix state, and a prefix state puts the answer in the corner.**

⚠️ **Getting this backwards produces working code with a wrong return, the hardest kind of bug to see**, because the table is full of correct numbers and you are reading the wrong one.

**Complexity, out loud:**

> *"O(m · n) time: one state per pair of prefix lengths, (m + 1)(n + 1) of them, and each is O(1), a comparison and an addition. O(m · n) space for the table, or O(min(m, n)) rolling, since the body only reads the previous row."*

## Subsequences, substrings and intervals

### Three sequence shapes

| The statement says | The state | The answer lives |
|---|---|---|
| **subarray, substring, contiguous, consecutive** | anchored: *"ending at `i`"*, *"ending at `(i, j)`"* | **an aggregate over the table** |
| **subsequence**: order kept, gaps allowed | a prefix: *"the first `i`"* | **the last cell** |
| **substring, where you need a fact about the piece itself** | an **interval**: *"the piece from `i` to `j`"* | depends on the question: a count or a best over all pieces is an aggregate, a fact about the whole input is one cell |

**Row 3 is a different shape**, and it is where the O(n³) solutions and the O(n²) tables with an O(1) body live (§Interval DP).

### The anchored family, and its inner loop

The anchored rule from §The failure mode covers a whole family of 1-D problems: the state is *the best thing ending at `i`*, and the answer is an aggregate over the table, not `dp[-1]`.

**Many members of that family can't answer the last decision in O(1).** When the last decision is *"which earlier position did I come from?"*, the body loops over every earlier position:

```python
for i in range(n):
    for j in range(i):
        if <j can come before i>:
            dp[i] = <combine>(dp[i], dp[j] + <step>)
```

> **That inner loop is the cost per state.** n states × O(n) each = **O(n²)**, and the sentence *"O(n²), because for each position I consider every earlier position as its predecessor"* is the analysis. **The count alone is not.**

### Interval DP

> **`dp[i][j]` is the answer for the piece `s[i..j]`.** One state per interval, about n²/2 of them.

**Two things make this shape distinctive.**

**First, the iteration order is by LENGTH.** The recurrence reads shorter intervals, `dp[i + 1][j − 1]`, or `dp[i][k]` and `dp[k + 1][j]`, and neither `i` ascending nor `j` ascending guarantees those are written:

```python
for length in range(1, n + 1):                # the axis the dependencies are monotone along
    for i in range(n - length + 1):
        j = i + length - 1
        ...
```

**The equivalent loop, easier to get right under pressure:** `i` **descending** and `j` **ascending from `i`**. Then `dp[i + 1][…]` is a later row, already done, and `dp[…][j − 1]` is an earlier column of this row, already done. **Both are §The iteration order applied to the subscripts.**

**Second, the recurrence often chooses a split point.**

```python
dp[i][j] = <combine> over k in i .. j - 1 of (dp[i][k] + dp[k + 1][j] + <join cost>)
```

> **About n²/2 states × up to n split points each = O(n³).** That is the canonical interval-DP cost, and you should recognise it. **The split must leave two independent halves**, which is the optimal-substructure test from §Optimal substructure: "is the best answer built from best answers to the parts?" asked about the two sides of `k`.

⚠️ **A check on the piece itself, written as a slice, is O(n) per cell.** `s[i:j + 1] == s[i:j + 1][::-1]` inside a double loop over `(i, j)` is O(n³) and reads like one short line. **The point of an interval table is to replace an O(n) check on a piece with an O(1) read of smaller pieces' stored answers.**

## The rolling array

> **Look at how far back the recurrence reaches. That is how many rows or cells you need to keep.**

It is read off the same subscripts as the order.

| The body reads | Keep | Space |
|---|---|---|
| `dp[i − 1]` only | **one variable** | O(1) |
| `dp[i − 1]`, `dp[i − 2]` | **two variables** | O(1) |
| `dp[i − c]` for many different `c` | **the whole array** (§1-D DP) | O(n) |
| `dp[r − 1][*]` and `dp[r][< c]` | **the previous row, plus the current one** | O(cols) |
| `dp[i + 1][j − 1]`, an interval | **the whole table**: there is no single axis to roll along | O(n²) |

**The 1-D O(1) version, and the thing that makes it go wrong:**

```python
def fib(n):
    a, b = 0, 1                          # F(0), F(1)
    for _ in range(2, n + 1):
        a, b = b, a + b                  # the whole right-hand side is evaluated first
    return b
```

`fib(10)` returns 55. ⚠️ **Written as two statements it breaks:** `a = b` then `b = a + b` reads the *new* `a`, so `b` doubles every step and `fib(10)` comes out 512. **Python's tuple assignment evaluates the whole right-hand side before binding any name**, which is why it is the safe form. It is the same family as saving a pointer before you overwrite it in a linked-list reversal ([05-linked-lists.md](05-linked-lists.md#in-place-reversal), §In-place reversal).

### The one-row form and its clobbering trap

Compressing a 2-D table into one row means each write destroys a value a later read might want. **Which direction is safe depends on which cell you need:**

| You need | So iterate the inner index |
|---|---|
| `dp[r − 1][c − 1]`, the **previous row**, one to the left | **descending**, or stash the diagonal in a variable before overwriting it |
| `dp[r][c − 1]`, the **current row**, one to the left | **ascending**: it is already updated, which is what you want |
| both | **ascending, with a one-variable stash of the value before it is overwritten** |

> **This is the knapsack direction rule generalised: ascending reads the current row, descending reads the previous one. Decide which you mean.**

On the grid from §The grid, rolled into one row with `dp[c] = grid[r − 1][c − 1] + min(dp[c], dp[c − 1])`, the ascending loop returns 7 and a descending one returns 5: descending reads `dp[c − 1]` before this row has written it, so it holds the cell above and to the left, and the loop has silently allowed a diagonal step.

⚠️ **Offer the rolling array; write the 2-D table first.** *"I'd write the full table for clarity, and note it's O(n) space because only the previous row is read"* earns the point and costs no bugs. **Compressing under pressure is where the silent ones come from.**

### Rolling destroys reconstruction

If the problem asks for **the path, the subsequence or the edit script itself** rather than its length, **you need the whole table.** You reconstruct by walking backwards from the answer cell, asking at each step *"which term of my recurrence produced this value?"*

> **Keep the table, or keep parent pointers. A rolling array has thrown the evidence away.**

**Say it out loud when you compress:** *"this gives O(n) space, but it can no longer reconstruct the subsequence; for that I'd keep the full table."* That sentence is the difference between having optimised and having noticed what the optimisation cost.

## When it is not DP

### Worked: Jump Game (LC 55)

[Jump Game](https://leetcode.com/problems/jump-game/) (LC 55). *Each element is a maximum jump length from that index. Starting at index 0, can you reach the last index?*

**The DP is obvious, and it is quadratic.** `dp[i]` is "index `i` is reachable", and `dp[i]` is `True` if some earlier `j` is reachable with `j + nums[j] >= i`. n states × O(n) each = **O(n²)**.

**The greedy is linear and needs no table:**

```python
def can_jump(nums):
    reach = 0                            # the furthest index reachable so far
    for i, jump in enumerate(nums):
        if i > reach:
            return False                 # a gap you can't cross
        reach = max(reach, i + jump)
    return True
```

It returns `True` on `[2, 3, 1, 1, 4]`, `False` on `[3, 2, 1, 0, 4]` (every route lands on index 3, whose jump is 0), and `True` on `[0]`, where the start is already the end.

> **The greedy is licensed by a proof, not by intuition: reachability is *downward closed*.** If you can reach index `k`, you can reach every index below it, because the jump that reached `k` from some `j < k` could have stopped anywhere between `j` and `k`. So one number, *the furthest index reachable so far*, is a complete summary of the past. **There is no choice to make, so nothing to enumerate, so no table.**

**The test that tells you a greedy is allowed:**

> **Can I prove that taking the locally best option never rules out a globally best answer?** That proof is an **exchange argument**: *"take any optimal solution that disagrees with my greedy choice at the first step, and show I can swap in my choice without making it worse."*

**And the honest interview move when you can't prove it:**

> *"There may be a greedy here: the DP is O(n²) and the structure looks monotone. But I can't prove the exchange argument on the spot, so I'll write the DP, which I know is correct, and say what I'd look for."*

⚠️ **An unproven greedy is a guess, and it is the one class of wrong answer that passes the examples and fails the tests.** A correct DP is never wrong, only sometimes slow. Give the correct one first and state its cost.

**This is Remember vs Reuse, one level up** ([01-arrays-hashing.md](01-arrays-hashing.md#the-three-escapes-remember-order-reuse), §The three escapes: Remember, Order, Reuse). Greedy is Reuse: a fixed number of summary values, O(1) space. DP is Remember: a table that grows with n. **The question is the same:** *"what is the least I must remember from the past to decide the present?"* If the honest answer is a single number, you have a greedy.

### The state is too big to enumerate

> **If your state has to include *"the set of things already used"*, you have 2ⁿ states, and a table with 2ⁿ rows is not a table.**

| n | 2ⁿ | Verdict |
|---|---|---|
| ≤ 20 | ≤ 2²⁰ = 1,048,576 | **bitmask DP**: the state is an `int` whose bits are the set, and it is DP (§Not covered here) |
| > 25 | > 2²⁵ ≈ 3.4 × 10⁷ | **backtracking with pruning.** This is module 07, and its exponential answer is the right one |

⚠️ **The tell is that the constraints are tiny.** `n ≤ 12` or `n ≤ 20` on an optimisation problem is the setter telling you the state is a subset. It is the same reading move as everywhere else: the bound names the intended complexity class.

### No overlapping subproblems

**Optimal substructure without overlap is divide and conquer.** Merge sort, quicksort, binary search. **A memo on merge sort never hits**: the two halves are disjoint, so no subproblem is asked for twice. Adding one costs memory and buys nothing.

### The summary test, in order

**Run these three, in this order, before you build a table:**

- **First: is the answer the candidates themselves?** Then backtracking. The path is in the state.
- **Second: is there a provable local rule?** Then greedy. No table.
- **Third: does the same subproblem come up twice?** If not, divide and conquer. If it does, **DP**.

## Every template, in one place

Twelve templates, in this order, because each is a row above it with a single change. The skeleton is §0.5, primitive 1.

| Row | Template | The delta from the row above | Invariant | Time · space |
|---|---|---|---|---|
| 1 | memoised recursion | (§0.5, primitive 1): `@cache` on a function of the state | each state's body runs at most once, and its result is final when stored | states × cost per state · the memo, plus O(depth) of stack |
| 2 | the same, tabulated | the calls become a loop, and you supply the order | every cell the body reads was written on an earlier iteration | the same time · the table, and no stack |
| 3 | 1-D, a fixed look-back, rolled | the table becomes a few variables | at the top of iteration `i`, the variables hold the cells `i` reads | O(n) · O(1) |
| 4 | 1-D, a choice per index | two options, skip `i` or take it, and taking it reaches back | `dp[i]` is the best using only the first `i` elements | O(n) · O(1) rolled |
| 5 | 1-D over a choice set | the inner loop is a set of choices, not a fixed pair | `dp[t]` is the answer for exactly `t`, or the sentinel if no choices reach `t` | O(target × choices) · O(target), pseudo-polynomial |
| 6 | each choice at most once | row 5 with the choices outside and the amount descending | after the first `k` items, `dp[t]` says whether the first `k` items can make `t` | O(items × target) · O(target) |
| 7 | counting: orderings or sets | `sum` instead of `min`, and the loop nesting decides what is counted | `dp[t]` is the number of ways to make `t`, and `dp[0] = 1` | O(choices × target) · O(target) |
| 8 | a grid | the state is a cell; dependencies come from above and from the left | `dp[r][c]` is the answer for `grid[r − 1][c − 1]` | O(rows × cols) · O(cols) rolled |
| 9 | two sequences | the state is a prefix of each input; match or mismatch | `dp[i][j]` is the answer for `a[:i]` against `b[:j]` | O(m · n) · O(min(m, n)) rolled |
| 10 | contiguous or subsequence | one branch of row 9, and the return, flip together | contiguous: the run ending at `(i, j)`; subsequence: the best over both prefixes | as row 9 |
| 11 | intervals | the state is a range, filled by length | every interval shorter than the current one is already filled | O(n³) with a split point · O(n²) |
| 12 | a mode, or a graph | the extra axis is a mode, not an index; or the states have no loop order | `f(i, mode)` is the best from `i` on, given the mode; `f(node)` is final when stored | states × transitions · the memo |

> **Read it as one algorithm and eleven deltas.**

Notes on the rows:

- **Every row has a state sentence, and you say it before you write the row.** *"`dp[…]` is the answer to ⟨exactly which subproblem⟩, the last decision is ⟨what⟩, and the answer lives in ⟨which cell⟩."*
- **Rows 6 and 7 are row 5 with one switch thrown.** Row 6 flips the amount loop to descending; row 7 changes the combiner to `sum` and makes the nesting matter. Neither raises when you throw the wrong switch.
- **Row 12 is the only row where top-down is forced.** Everywhere else you choose it.

**Row 1, memoised recursion:**

```python
from functools import cache

@cache
def f(state):
    if <base state>:
        return <the identity of the combiner>
    return <combine>(<cost of c> + f(<state after c>) for c in <choices>)

return f(<the whole problem>)
```

The arguments must be hashable, and something must shrink on every call (§Something must shrink, and the states must form a DAG). The base case returns the combiner's identity (§The three combiners).

**Row 2, tabulated:**

```python
dp = [<sentinel or identity>] * (n + 1)
dp[0] = <base>
for i in range(1, n + 1):                 # the only new decision: the order
    dp[i] = <combine>(... dp[<smaller>] ...)
return <the cell, or the aggregate, that line 3 named>
```

Start the loop after the base cases, or the first iteration reads `dp[-1]`, which is the last cell (§0.6).

**Row 3, a fixed look-back, rolled:**

```python
a, b = <dp[0]>, <dp[1]>
for i in range(2, n + 1):
    a, b = b, <combine>(a, b)             # the whole right-hand side first
return b
```

Two statements instead of one tuple assignment read the new `a` (§The rolling array).

**Row 4, a choice per index:**

```python
for i in range(<first index past the seeds>, n + 1):
    dp[i] = <combine>(dp[i - 1],                          # skip element i
                      dp[i - <reach back>] + value(i))    # take it
return dp[n]
```

How far back it reaches is read off the problem's constraint, not memorised (§The shape one delta away: a choice per index).

**Row 5, over a choice set:**

```python
dp = [<sentinel>] * (target + 1)
dp[0] = <identity>
for t in range(1, target + 1):
    for c in <choices>:
        if c <= t:                        # load-bearing: dp[t - c] would wrap
            dp[t] = <combine>(dp[t], dp[t - c] + <step cost>)
return <dp[target], with the sentinel translated>
```

The sentinel inside, the problem's "impossible" value only at the return (§Kind 2: the impossible state, and the sentinel that survives your combiner). This is the target-sum search of module 07 with a combiner in place of a list of paths.

**Row 6, each choice at most once:**

```python
dp = [False] * (total + 1)
dp[0] = True
for x in nums:
    for t in range(total, x - 1, -1):     # descending
        dp[t] = dp[t] or dp[t - x]
```

Descending is the whole difference from row 5. Ascending lets `dp[t − x]` already include `x`, which is reuse, a different problem with no error (§The direction bug that has a name: 0-1 knapsack in one row). The 2-D form `dp[k][t]` is easier to explain; write it first and roll it after.

**Row 7, counting, with the target outside:**

```python
dp = [0] * (target + 1)
dp[0] = 1                                 # one way to make nothing
for t in range(1, target + 1):            # the target outside: every ordering counted
    for c in <choices>:
        if c <= t:
            dp[t] += dp[t - c]
```

With choices `[1, 2, 3]` and a target of 4 this counts 7: `1+3` and `3+1` are two answers. **Swap the nesting, choices outside and `t` ascending from `c`, and it counts each set once, 4 here**, because a choice is only ever added after the choices already processed, so each set is built in one fixed order. It is the `start` parameter of module 07 written as a loop nesting ([07-backtracking.md](07-backtracking.md#start-one-parameter-three-jobs), §`start`: one parameter, three jobs), and the statement decides which one you want.

**Row 8, a grid:**

```python
dp = [[<sentinel>] * (cols + 1) for _ in range(rows + 1)]   # padded: no boundary ifs
dp[0][1] = <the entrance value>
for r in range(1, rows + 1):
    for c in range(1, cols + 1):
        dp[r][c] = <cell value> + <combine>(dp[r - 1][c], dp[r][c - 1])
return dp[rows][cols]
```

Say the offset in line 1 (§The grid). The memo is legal only because the moves can't cycle.

**Row 9, two sequences:**

```python
dp = [[<base>] * (n + 1) for _ in range(m + 1)]   # row 0 and column 0: the empty prefixes
for i in range(1, m + 1):
    for j in range(1, n + 1):
        if a[i - 1] == b[j - 1]:
            dp[i][j] = <from dp[i - 1][j - 1]>
        else:
            dp[i][j] = <combine over the terms the problem allows>
return <the corner, or the aggregate>
```

The candidate terms are `dp[i − 1][j]` (skip from `a`), `dp[i][j − 1]` (skip from `b`) and `dp[i − 1][j − 1]` (use both). **Which of them the problem allows, and at what cost, is the problem.** Name each one in English before you write it. `a[i − 1]`, not `a[i]`: the table is offset by one and the input is not.

**Row 10, contiguous or subsequence,** is a change to two lines of row 9, not a new template: the mismatch branch and the return. The table in §Substring or subsequence: one branch and one return says which way each goes.

**Row 11, intervals:**

```python
for length in range(2, n + 1):            # the axis the dependencies are monotone along
    for i in range(n - length + 1):
        j = i + length - 1
        dp[i][j] = <combine>(dp[i][k] + dp[k + 1][j] + <join cost>
                             for k in range(i, j))
```

The length-1 intervals are the base cases, filled before the loop. Or loop `i` descending and `j` ascending from `i` (§Interval DP).

**Row 12, a mode, or a graph:**

```python
@cache
def f(i, mode):                           # mode is one of a small fixed set
    if i == n:
        return <terminal value for mode>
    return <combine>(<transition cost> + f(i + 1, nxt) for nxt in <modes legal from mode>)

@cache
def f(node):                              # no loop order exists: let the recursion find it
    return <step> + <combine>((f(nxt) for nxt in <successors of node>), default=<value at a sink>)
```

**The mode is the fact a single number couldn't carry**, added as a dimension instead of as a special case. For the graph form, **the memo is legal only if the successor relation can't cycle**, so say which condition in the statement makes it a DAG. That is module 08's BLACK mark carrying a value: each node computed once, O(V + E), which on a grid is O(rows × cols). The `default=` covers a node with no successors (§The empty problem and the empty choice set).

## How to attack a DP problem

1. **Name the pattern and the signal that pointed to it**, before any code. *"'The fewest', a target in the constraints, and n up to 10⁴"* is a signal (§0.8).
2. **Run the acid test.** Can two explorations disagree about the same state? **No: the state has an answer of its own, so cache it.** Yes: you're in module 07, and there is no memo (§The acid test).
3. **Write the state sentence, three lines, before any code** (§The state sentence, before any code):
   - **`dp[i]` is the answer to ⟨exactly which subproblem⟩**, every index named, in the problem's nouns, with a unit.
   - **The recurrence is ⟨…⟩, because the last decision is ⟨…⟩.**
   - **The base case is ⟨…⟩, and the answer lives in ⟨which cell, or which aggregate⟩.**
4. **What shrinks?** An index, an amount, a remaining length. Name it, or there is no base case and no order.
5. **Top-down or bottom-up, and why?** One clause (§Top-down and bottom-up).
6. **If bottom-up: list the cells the body reads, and check each is already written** (§The iteration order).
7. Write it.
8. **Run [bug-checklist.md](../reference/bug-checklist.md#the-30-second-pass), §The 30-second pass**, then §Common DP mistakes below. Then, specific to here: *is my sentinel absorbing?* · *does the loop start after the base cases?* · *`[[x] * n for _ in range(m)]`, not `[[x] * n] * m`?* · *last cell or an aggregate?* · *what did my last fix make unnecessary?*
9. **Trace the base cases and the degenerate cases, not the happy path:** empty input, one element, the smallest input where the recurrence fires, and the state the problem calls impossible (§The base cases to trace, every time).
10. **Say the complexity unprompted, time and space**: *"O(\_\_) because there are \_\_ states, one per ⟨noun⟩, and each costs \_\_."* Count the table as space, then offer the rolling array (§0.7).
11. **Then: is it optimal?** What must any correct algorithm do at minimum? And the honest upgrade: *"the inner loop is O(k); if n were larger I'd look for a way to make it O(log k)."*

## In depth

The derivations and measurements behind the rules above. Read them once, then come back when a rule stops making sense.

### What to store the memo in: a matrix or a dict

A separate decision from top-down versus bottom-up. The discriminator is **whether the state space is dense or sparse.**

| | **A list of lists**, `[[None] * n for _ in range(n)]` | **A dict**, including `@cache` |
|---|---|---|
| Keys must be | small non-negative ints, with bounds known up front | anything hashable: strings, tuples, negatives, unbounded |
| Cost per access | index arithmetic | build the key, then hash it |
| Memory per state | 8 bytes, one pointer | about 124 bytes measured, for a tuple key of two ints |
| A sparse state space | allocates every cell, reached or not | pays only for the states reached |
| A negative index | wraps to the end of the list, silently | raises `KeyError` |

> **The list is faster. The dict is safer and more general.**

**Dense: use a list.** An interval DP over `(i, j)` asks for every pair with `i ≤ j`.

**Sparse: use a dict.** `f(i, remaining)` where `remaining` can range up to 10⁹ but only a few hundred values are reachable. A list would allocate a billion cells to use three hundred ([04-binary-search.md](04-binary-search.md#never-materialise-the-search-space), §Never materialise the search space).

⚠️ **The last row of the table is the trap.** `dp[-1]` reads the last cell with no exception; a dict raises. When the state can go negative, offset it into the list deliberately, or use a dict ([bug-checklist.md](../reference/bug-checklist.md#a-negative-index-wraps-instead-of-crashing), §A negative index wraps instead of crashing).

⚠️ **`None` is the "not computed" marker, not `False` and not `0`**, because it must be a value the answer can never take. `if dp[i][j]:` recomputes every cached `False` and every cached `0`, forever.

> **The interview move: write the `@cache` version first, because it is shorter, can't wrap and works whatever the state is. Then say *"the states here are dense integers, so I'd back this with a list instead: no hashing, 8 bytes a cell rather than over a hundred."*** That sentence separates the algorithm's complexity from what it costs to run.

**Why the gap is so large.** A dict is a list plus a function that turns your key into an index. **If your key already is an index, you are paying for a function you don't need.** One `memo[(i, j)]` access does this:

| Step | Cost |
|---|---|
| build the key: `(i, j)` creates a tuple object | 56 bytes for a two-element tuple |
| hash it: hash each element and combine | proportional to the key's size |
| probe: index the slot table, compare the stored key, re-probe on a collision | at least one extra memory read |
| on a store past the load factor: allocate a bigger table and re-insert every key | amortised, and a real spike |

One `memo[i][j]` access indexes the outer list, then the row. No allocation, no hashing, no comparison, no resize. Every int outside the cached range −5 to 256 is a separate 28-byte object on top, in either structure, but the dict also holds it inside a key.

**Measured:** a dict holding the 500,500 pairs `(i, j)` with `0 ≤ i ≤ j < 1000` takes about 62 MB, roughly 124 bytes an entry. A 1000 × 1000 list of lists takes about 8 MB.

### Why dense is the right discriminator

> **A list's cost is proportional to the bounding box of the state space. A dict's is proportional to the states you reach.** Compare those two numbers; the comparison is the decision.

| | Reached ≈ box: **dense** | Reached ≪ box: **sparse** |
|---|---|---|
| **List** | pays for what you use, with no per-state overhead | allocates the whole box |
| **Dict** | pays a per-state overhead for a mapping you don't need | pays only for the reached set |

**The interval DP:** the box is n², the reached set about n²/2. The same order, so a list. **`f(i, remaining)` with `remaining` up to 10⁹ and 300 values reachable:** a dict.

"Small non-negative ints" is the same fact from the other side. A list index is a memory offset. Any key that isn't already an offset has to be mapped to one, and mapping is exactly what hashing does. A string key, a tuple key, a negative key, a key spanning 10⁹: each is a reason you need the function, and so a dict.

### Building the matrix: why the short form is broken

```python
dp = [[-1] * n for _ in range(m)]     # m independent rows
dp = [[-1] * n] * m                   # m names for one row
```

**`*` on a list repeats references, not contents.** Two lines prove it:

```python
dp = [[-1] * 3] * 3
dp[0][0] = 99
print(dp)          # [[99, -1, -1], [99, -1, -1], [99, -1, -1]]
```

In a DP, the table now holds n cells instead of m · n, so every state in the same column collides. With `find_length` from §Two sequences built this way, `[1]` against `[1, 1]` returns 2, a common run longer than the shorter input; the answer is 1. It doesn't crash.

**Why the inner `* n` is fine and the outer one isn't:**

| | The element repeated | Mutable? | Safe? |
|---|---|---|---|
| `[-1] * n` | the int `-1` | no | **yes**: an int can't change in place, so the sharing is invisible |
| `[[-1] * n] * m` | a list | yes | **no**: `dp[0][0] = x` changes the shared row, and every name sees it |

> **`*` is safe exactly when the repeated element is immutable.** Safe: `[0] * n`, `[False] * n`, `[None] * n`, `[float('inf')] * n`. Broken: `[[…]] * m`, `[[]] * n`, `[set()] * n`, `[{}] * n`.

So a 1-D table is always safe, and the trap appears the moment the table becomes 2-D. The comprehension works because it runs `[-1] * n` m times and makes m row objects, instead of evaluating it once and repeating the result. It is the same fact as `res.append(path)` against `res.append(path[:])` in module 07: `=` binds a name, `append` stores a reference, and `*` repeats a reference, and none of them copies.

**The detection test:** *after I write one cell, does another cell change?* If it does, you have one object and several names.

### Converting top-down to bottom-up

Four steps. Only the last needs thought.

| Step | |
|---|---|
| 1 | **The parameters of `f` become the axes of the table.** `f(i)` becomes `dp[i]`, `f(i, j)` becomes `dp[i][j]`, and the ranges of the parameters are the dimensions |
| 2 | **The base cases become the initialisation.** `if i == 0: return 1` becomes `dp[0] = 1` |
| 3 | **The body becomes the loop body**, with every `f(x)` rewritten as `dp[x]` |
| 4 | **Choose loops so that every cell the body reads is already written** (§The iteration order) |

Converting the other way is steps 1 to 3 in reverse, and step 4 disappears, which is why top-down is easier to get right under pressure.

⚠️ **Step 1 is where the answer's location changes.** Top-down, you call `f(n)` and you're done. Bottom-up, you have to say which cell holds the answer, and if the state is anchored, it is an aggregate over the table (§The failure mode: a state that can't express the answer). The conversion is where that bug gets written.

### When it TLEs anyway: three causes, three fixes

A solution with the right complexity can still run out of time. "Too slow" has three causes:

| Symptom | Cause | Fix |
|---|---|---|
| the operation count is a bigger power of n than the bound allows | the wrong complexity class | a different algorithm |
| the right class, but you visit states that can't contribute | too many states explored | prune |
| the right class and the right states, but each one is expensive to touch | the per-state constant | change the data structure |

> ⚠️ **Pruning buys nothing when nothing is being wasted.** If every state is needed, every state has to be filled; the fix is to make each one cheaper.

**Read the numbers together, not just the time.** A memory figure many times the cell count × 8 bytes names row 3 on its own: the per-state overhead is the problem, not the count.

**The three overheads a top-down solution pays, and which of them need a loop:**

| What's costing you | Fix | Still recursive? |
|---|---|---|
| a dict keyed by tuples: a tuple built and hashed per access, about 124 bytes an entry | memoise into a list indexed by ints | **yes** |
| about one Python function call per state | go iterative | no |
| a stack deeper than about 1,000 frames | go iterative | no, forced ([00-before-you-start.md](00-before-you-start.md#stack-depth), §Stack depth) |
| you need a rolling array | go iterative | no, forced |

```python
dp = [[None] * n for _ in range(n)]      # None = not computed; 8 bytes a cell
def f(i, j):
    if dp[i][j] is not None:             # no tuple, no hash
        return dp[i][j]
    ...
```

> **"Recursion is too slow, so go iterative" is the wrong rule.** Name which overhead is biting, the key, the calls or the stack, and fix that one. The first is fixable without giving up recursion.

## Not covered here

- **Bitmask DP:** the state is a subset held in an `int`, for n up to about 20 (§The state is too big to enumerate).
- **DP on trees:** the state is a node plus a mode, and post-order is the iteration order.
- **Digit DP:** counting the numbers up to a bound that have some property, one digit at a time.
- **Matrix exponentiation** for a linear recurrence at huge n, in O(log n).
- **The look-back optimisations** that take an O(n²) anchored DP to O(n log n) or O(n) with binary search or a monotonic structure, and the convex hull trick and Knuth's optimisation beyond them.
- **Shortest paths on a state graph with cycles.** The memo needs a DAG; with cycles and non-negative costs, use [08-graphs.md](08-graphs.md#dijkstra), §Dijkstra, whose heap you'll see later, in module 10 ([10-heaps.md](10-heaps.md)).

Interview loops mostly ask 1-D linear DP, a coin-change or knapsack-style problem, one grid and one two-sequence problem. Interval DP comes up occasionally, and bitmask DP rarely. If one of the rarer shapes comes up, one sentence is enough: *"this is O(n²) because each position considers every earlier one as its predecessor; if n were 10⁵ I'd look for a way to make that inner search O(log n), with a sorted structure or a monotonic deque, rather than a different state."*

## Self-check answers

1. **BFS's mark is a boolean, and the first arrival is final**: once a cell is marked, every later arrival is thrown away, so the second path to a cell is never counted. **A memo holds an answer, and the answer combines every predecessor**: the count at a cell is the sum of the counts at the cells that lead into it, which needs all of them, not the first.
2. **15 calls over 6 distinct states**, `F(0)` to `F(5)`. A memo makes each state's body run once, so 6 bodies instead of 15 calls' worth of work, and the growth goes from exponential to linear. It doesn't change the recurrence, the answer, or the tree you would draw: **the memo collapses the tree onto its labels**, so each label is solved once and every repeat is a lookup.
3. `dp[-1]` is the best subarray **ending at the last index**, not the best subarray. The answer is `max(dp)`. On that input `dp` is `[-2, 1, -2, 4, 3, 5, 6, 1, 5]`, so `dp[-1]` **returns 5, not 6**: the best run, `[4, -1, 2, 1]`, ends earlier.
4. **The empty problem has exactly one solution, doing nothing, so it counts 1.** A state with no legal move has no way to finish, and the count is the sum over its moves, a sum over nothing, which is 0. Seed the empty problem with 0 and every count comes out 0.
5. **`-1` is smaller than every real cost, so `min` picks it every time**, and one impossible cell poisons every cell that reads it. Use `float('inf')`, which loses every `min`. A `-1` the problem asks for belongs **only at the return**: translate the sentinel there, and nowhere else.
6. **No, it is still top-down.** The direction of the index doesn't decide it. **The test is whether the code recurses or loops:** a recursive, memoised function is top-down whichever end it starts from, because the call stack picks the order. Bottom-up means a loop whose order you chose.
7. **Ascending reads cells the current item has already updated, so the item gets used again**: you have written the unbounded version. With weights `[3]` and a total of 6, the ascending loop sets `dp[6]` to `True`, using 3 twice, where the 0-1 answer is `False`. **There is no error**, because every read is a legal index holding a legal value; it is the wrong value.
8. **Every row is the same list**, so `dp[0][0] = 1` shows up in every row: `dp[r][0]` is 1 for all `r`. The inner `* n` repeats an int, and an int is immutable, so sharing it is invisible. **The outer `* m` repeats one list**, and a list is mutable, so a write through any name is seen through all of them.
